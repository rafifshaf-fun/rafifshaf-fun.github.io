MLOps Tanpa Burnout

📅 April 2024 ⏱️ 7 menit baca 🏷️ MLOps · Docker · MLflow · Grafana

Sebagian besar panduan MLOps umumnya mengasumsikan keberadaan cluster Kubernetes, tim DevOps khusus, dan alokasi anggaran cloud yang besar. Padahal realitas di lapangan sering kali jauh lebih ramah: sebuah server VPS dengan 4 vCPU, RAM 8GB, Docker Compose, dan keinginan kuat untuk menghasilkan sistem yang stabil.

Saya mengelola alur kerja MLOps ini dari Garut, Jawa Barat. Artikel ini merangkum strategi membangun infrastruktur Machine Learning yang stabil dan hemat biaya tanpa mengalami kelelahan kerja (burnout).

Berikut rincian komponen krusial yang perlu disiapkan beserta opsi yang dapat ditunda:

✅ Komponen Wajib

  • Experiment tracking (MLflow): Pengelolaan hyperparameter dan hasil eksperimen secara terpusat. MLflow bersifat open-source, fleksibel di berbagai lingkungan, dan efisien untuk diintegrasikan.
  • Containerisasi (Docker): Menghilangkan isu ketidaksesuaian lingkungan ("works on my machine"). Konfigurasi Docker Compose memudahkan pengelolaan alur kerja dalam satu file docker-compose.yml.
  • Pemantauan sistem (Grafana): Tanpa pemantauan penyimpangan (drift) hasil prediksi, penurunan performa model sulit terdeteksi. Dasbor Grafana memberikan visibilitas real-time atas kesehatan sistem.
  • Manajemen versi model (Versioning): MLflow Model Registry memfasilitasi pelacakan status versi model (staging, production, archived) secara transparan dari fase pelatihan awal.

❌ Komponen yang Dapat Ditunda

  • Kubernetes: Docker Compose sudah mencukupi untuk kebutuhan deployment pada satu server (single-node).
  • Feature store kompleks (Feast/Tecton): Skema tabel PostgreSQL bertipe data versi sudah memadai pada tahap awal.
  • Pipeline CI/CD otomatis: Eksekusi retraining manual via API MLflow tetap efektif untuk pengelolaan skala mandiri.
  • Versioning data tingkat lanjut (DVC): Penggunaan Git LFS atau struktur direktori terorganisir sudah mencukupi untuk dataset skala kecil hingga menengah.
  • Framework serving kompleks (TorchServe/Triton): Pemanfaatan FastAPI sebagai pembungkus model lebih sederhana dan mudah dianalisis.

File docker-compose.yml Utama

# Stack yang berjalan di atas VPS $20/bulan
version: '3.8'
services:
  mlflow:
    image: ghcr.io/mlflow/mlflow:v2.12.0
    ports: ["5000:5000"]
    command: mlflow server --host 0.0.0.0 --backend-store-uri postgresql://...
    restart: unless-stopped

  grafana:
    image: grafana/grafana:10.4.0
    ports: ["3000:3000"]
    volumes: ["./grafana/dashboards:/etc/grafana/provisioning/dashboards"]
    restart: unless-stopped

  prediction-api:
    build: ./api
    ports: ["8000:8000"]
    depends_on: [mlflow]
    restart: unless-stopped

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: mlops
      POSTGRES_USER: mlflow
    volumes: ["pgdata:/var/lib/postgresql/data"]
    restart: unless-stopped

Prinsip MLOps Efisien

1. Utamakan Teknologi Stabil (Boring Technology)

Gunakan PostgreSQL alih-alih database terdistribusi yang kompleks, FastAPI ketimbang framework serving rumit, serta Docker Compose alih-alih Kubernetes. Setiap keputusan teknologi hendaknya didasari pada kemudahan pemeliharaan dan analisis saat timbul kendala operasional.

2. Pemantauan Terukur

Indikator pemantauan dasar yang disarankan:

  • Distribusi prediksi historis: Visualisasi histogram harian untuk mendeteksi pergeseran pola data.
  • Penyimpangan fitur (Feature drift / PSI): Pengukuran Population Stability Index pada fitur utama dengan batas ambang jelas (PSI > 0.2).
  • Metrik latensi (p50/p95/p99): Menjamin kecepatan respons inferensi tetap berada dalam batas toleransi.
  • Catatan error (Error Rate): Pemantauan kegagalan inferensi, kondisi timeout, maupun luaran tak valid (NaN).

3. Pelatihan Ulang Berbasis Ambang Batas (Trigger-based Retraining)

Melatih ulang model secara berkala tanpa indikator yang jelas berpotensi melipatgandakan beban komputasi. Lebih disarankan untuk memicu alur retraining secara otomatis hanya ketika metrik drift terdeteksi melampaui batas toleransi yang ditetapkan.

4. Dokumentasikan Keputusan Teknis

Mencatat alasan di balik pemilihan algoritma atau struktur data dalam berkas DECISIONS.md pada repository akan mempermudah alur pemeliharaan sistem di masa mendatang.

Rencana Pengembangan Lanjutan

  • Integrasi feature store terstruktur saat pengolahan data mentah membutuhkan alur pemrosesan khusus.
  • Penerapan shadow deployment untuk menguji model baru secara paralel tanpa mengganggu alur production.
  • Penyusunan infrastruktur A/B testing untuk membandingkan performa antar model secara objektif.
  • Otomasi pencarian hyperparameter (Optuna) yang terhubung langsung ke dashboard MLflow.

Kesimpulan

Sebagian besar proyek Machine Learning tidak mengalami kegagalan akibat keterbatasan infrastruktur, melainkan akibat minimnya visibilitas terhadap performa model yang sedang beroperasi. Mulailah dengan experiment tracking dan pemantauan dasar, lalu tingkatkan kompleksitas sistem secara bertahap sesuai kebutuhan operasional.
